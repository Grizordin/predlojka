# Предложка: обновление 0.2.0 / adaptive-1

## Что загружать

В корень репозитория **Grizordin/predlojka**, в ветку, которую развёртывает ваш Render:

1. Заменить server.js.
2. Добавить adaptive-scheduler.js рядом с server.js — без него сервер не запустится.
3. Заменить package.json (версия 0.2.0, те же зависимости; добавлены команды проверок).
4. Добавить tests/adaptive.test.js и tests/server.test.js, если хотите запускать npm test.
5. README.md можно заменить этой инструкцией.

НЕ загружать node_modules, файлы из репозитория animeSSS-help, локальные выгрузки, секреты или архив целиком как один файл в GitHub.
Существующие schema.sql и client.user.js оставить. Никакой новой SQL-миграции не требуется.
Версию основного Tampermonkey-помощника для этого обновления повышать не нужно.

## Порядок развёртывания

1. Сделать резервную копию D1 или убедиться в доступности восстановления. Ничего не удалять и не переимпортировать.
2. В Render открыть существующий Web Service с адресом predlojka-o4s8.onrender.com.
3. В Settings проверить Repository и Branch. Должен быть нужный репозиторий predlojka. Если указан другой — сначала выяснить, какой сервис используется.
4. Загрузить перечисленные файлы в эту ветку GitHub. Все обязательные файлы публиковать одним коммитом.
5. Build Command оставить npm install, Start Command — npm start, Health Check — /health. Нужен Node.js не ниже 20.18.1; проверьте текущую версию в логе сборки.
6. Не менять логин, пароль, Cloudflare ID/токен и ADMIN_TOKEN. Не переносить секреты в код.
7. При включённом автодеплое дождаться завершения. Иначе Manual Deploy → Deploy latest commit.
8. Держать только ОДИН экземпляр сканирующего сервера на эту D1. Несколько экземпляров/два Render-сервиса на одной базе будут дублировать обход и перезаписывать расписание. Межпроцессная аренда в этом обновлении не реализована.
9. После загрузки дождаться первого цикла (~5 секунд после запуска плюс время загрузки D1). Проверить /health и /api/tick-status.
10. В /health должно появиться runtimeCache.schedulerVersion = "adaptive-1".
11. Получить защищённый отчёт GET /api/admin/authors с заголовком x-admin-token (существующий ADMIN_TOKEN). Не вставлять токен в URL или переписку. Отчёт отдаёт всех авторов, интервалы, сроки, ошибки и расход D1 с запуска.

Откат: вернуть предыдущий server.js и package.json из GitHub/Render. Старые рейтинги и контрольная запись runtime_checkpoint_v1 сохранены. Новую запись adaptive_authors_v1 удалять не нужно.

## Настройки и ограничения нагрузки

Значения по умолчанию:

| Переменная Render | Значение | Смысл |
|---|---:|---|
| ANIMESSS_REQUEST_DELAY_MS | 1000 | Не меньше 1 секунды между запросами к сайту; большая ранее заданная пауза сохраняется |
| SUGGESTION_REQUESTS_PER_HOUR | 600 | Верхний темп попыток обхода предложки |
| REPLACEMENT_REQUESTS_PER_HOUR | 300 | Общий верхний темп поиска авторов замен/возвращённого голосования |
| CARDS_MONITOR_INTERVAL_MS | 60000 | Проверка каталога и текущих голосований |
| TICK_BUDGET_MS | 35000 | Рабочее окно цикла; значение ограничено 5–45 секундами |
| RUNTIME_CHECKPOINT_INTERVAL_MS | 300000 | Сохранение расписания и прогресса раз в 5 минут |

Существующие более осторожные настройки не повышать вслепую. Новые переменные можно не создавать — сработают defaults.
Старые SUGGESTION_RATED_INTERVAL_MS, SUGGESTION_ZERO_INTERVAL_MS и SUGGESTION_DECAY_DAYS больше не управляют автоматическим обходом.
Исторические баллы не обнуляются. Проверка профилей остаётся ручной: она не нужна для исключения авторов, потому что теперь никто не исключён из редкого обхода.

600/300 — потолки темпа, НЕ обещание такого числа фактических запросов. При окне 35 секунд в минуту расчёт частоты предложки консервативно использует примерно 350 проверок/час. Долгие ответы, D1, ошибки и сон Render могут снизить пропускную способность ещё сильнее. Просрочки видны в отчёте.
Резерв только на обход 1075 авторов раз в 12 часов — примерно 90 страниц/час. Запросы авторизации, мониторинг каталога и повторы учитываются отдельно; все идут через общий последовательный клиент.

## Что изменилось

- Рейтинг 0–100: 60% — логарифмический объём новых уникальных карт за 14 дней, 40% — дни находок за 7 дней; после прекращения находок рейтинг затухает.
- Исторические баллы служат ограниченной начальной оценкой и теряют влияние за 14 дней.
- Желаемый интервал: 720 / (1 + 71 * (rating/100)^2) минут. Дополнительная частота масштабируется под бюджет.
- Отмеченные неактивными не исключаются: для них действует редкий обход, обычно раз в 12 часов.
- При первом запуске старые/неизвестные сроки равномерно распределяются на ближайшие интервалы (до 12 часов). Это одноразовый переходный период, не мгновенный полный обход.
- При последующих перезапусках сохраняются индивидуальные сроки. Контрольное сохранение раз в 5 минут означает, что при аварийном завершении возможно повторение части последних пяти минут, но не полное перераспределение.
- Новая наблюдаемая публикация с data-author в каталоге снимает inactive и ставит ближайшую проверку, затем временный ускоренный режим на сутки. Одна и та же публикация не вызывает пробуждение каждую минуту.
- Публикация уже известной карты предложки не начисляет второй балл. Источник времени — обнаружение, не точная дата подачи на сайт.
- Один просмотр замен автора сопоставляется со всеми текущими неизвестными заменами. Ошибки не засчитываются как успешная проверка автора.
- Не найденные авторы актуальных замен повторно ищутся спустя 12 часов. Старые задачи отсутствующего S-голосования не удаляются и не тратят очередь.
- Поиск S-авторов включается только при наличии распознанного блока голосования, и при поиске одновременно обновляет предложку.
- Очереди по очереди получают рабочие слоты. Нет безусловного «сначала завершить весь поиск авторов».
- HTTP/сетевые сбои включают backoff; подозрительные страницы проверки браузера не принимаются за пустой список.
- Полный отчёт доступен через /api/admin/authors; требует ADMIN_TOKEN, без ограничения 500.

Сканируется каталог /cards/ и страницы авторов, как в исходном проекте. Это не полный обход всех страниц каталога. Изменение разметки или пагинации потребует отдельной проверки.

## Cloudflare D1: сохранена экономия

- Полная загрузка таблиц в память только при старте; очереди и отчёты используют память.
- Неизменившаяся предложка и повторно просмотренный каталог не создают запись в D1 на автора.
- Обычный прогресс обхода сохраняется одной сжатой записью settings/adaptive_authors_v1 раз в 5 минут (до ~288 обновлений строки/сутки при непрерывной работе).
- Старая runtime_checkpoint_v1 также сохраняется пакетно. SQL-схема и исторические баллы остаются.
- Сжатие выполняется асинхронно. Размер значения ограничен 1.5 MB с запасом к лимиту D1 в 2 MB на строку/значение.
- Новые карты, изменения статусов и окончательные результаты пишутся по фактическим изменениям.
- Повтор одинаковой ошибки сохраняется в D1 не чаще одного раза за 5 минут; оперативные сообщения остаются в ограниченном журнале в памяти.
- Отчёт показывает d1UsageSinceStartup из meta.rows_read/rows_written ответов D1. Это расход только этого процесса с запуска, НЕ суточный расход всего аккаунта.

На D1 Free документация указывает 5 млн прочитанных и 100 тыс. записанных строк в сутки. Индексы и прочие сервисы тоже влияют на расход. Фактические квоты аккаунта и тариф здесь не проверялись:
https://developers.cloudflare.com/d1/platform/pricing/
https://developers.cloudflare.com/d1/platform/limits/

На Render Free сервис может уснуть после 15 минут без входящего трафика; внутренний setInterval не гарантирует непрерывной работы. Также возможны рестарты. Поэтому срок 12 часов достижим только при работающем сервере и доступном сайте. Тариф, внешние планировщики и существующие проверки доступности не менялись:
https://render.com/docs/free
